## Introduction

Context is part of React itself — no install, no dependency. These examples
target **React 19** (19.2.x at the time of writing).

The most useful thing to understand first: **Context is not a state manager.**
It holds no state of its own. It is a transport mechanism — a way to make a
value available to a subtree without threading it through every intermediate
component as props. The state itself still comes from `useState` or
`useReducer`; Context just distributes it.

That distinction explains most of the confusion around it. "Should I use Context
or Zustand?" is a slightly wrong question: Context is how a value gets *down the
tree*, and a state library is how a value is *stored and subscribed to*. They
overlap only because Context is often the simplest thing that works.

In React 19 the context object is itself the provider:

```jsx
<ThemeContext value={theme}>
  <Page />
</ThemeContext>
```

`<ThemeContext.Provider>` still works and is what you'll see in older code, but
it's now the legacy form.

## The one real limitation

When a provider's `value` changes, **every component reading that context
re-renders** — all of them, regardless of which part of the value they actually
use. Values are compared with `Object.is`, and wrapping a consumer in `memo`
does not save it, because context deliberately bypasses memoisation.

There is no selector API. You cannot say "re-render me only when
`value.user.name` changes." That single missing capability is the reason state
libraries exist, and it's the honest dividing line for when to leave Context
behind.

Two consequences follow, and both are avoidable:

1. An inline object as the value (`value={{ user, login }}`) creates a new
   reference on every render of the provider, so every consumer re-renders every
   time — even when nothing meaningful changed. Memoise it.
2. Bundling unrelated state into one context couples their update rates. A
   context holding both `theme` and `mousePosition` re-renders the theme
   consumers on every mouse move.

<DifficultyTabs>

<Level value="easy">

Create the context outside any component. The argument is the **default value**,
used only when a component reads the context with no provider above it:

```jsx
import { createContext, useContext } from 'react'

const ThemeContext = createContext('light')
```

Provide a value to a subtree, and read it anywhere inside:

```jsx
function App() {
  return (
    <ThemeContext value="dark">
      <Toolbar />
    </ThemeContext>
  )
}

function Button() {
  const theme = useContext(ThemeContext)
  return <button className={theme}>Click me</button>
}
```

`Button` can be nested arbitrarily deep — nothing in between needs to know the
theme exists. That's the whole point.

To make it stateful, pair it with `useState` in the provider component:

```jsx
function App() {
  const [theme, setTheme] = useState('light')

  return (
    <ThemeContext value={theme}>
      <Toolbar />
      <button onClick={() => setTheme('dark')}>Go dark</button>
    </ThemeContext>
  )
}
```

</Level>

<Level value="medium">

**Wrap it in a custom hook.** This hides the context object, gives you one place
to add logic, and turns "no provider" from a silent bug into a loud one:

```jsx
const ThemeContext = createContext(null)

export function useTheme() {
  const context = useContext(ThemeContext)
  if (context === null) {
    throw new Error('useTheme must be used inside <ThemeProvider>')
  }
  return context
}
```

Using `null` as the default and throwing is usually better than a plausible
fallback, which would let a missing provider fail quietly and confusingly.

**Memoise the value when it's an object.** Without this, every render of the
provider hands consumers a fresh reference and re-renders all of them:

```jsx
import { useCallback, useMemo, useState } from 'react'

function AuthProvider({ children }) {
  const [currentUser, setCurrentUser] = useState(null)

  const login = useCallback((response) => {
    setCurrentUser(response.user)
  }, [])

  const value = useMemo(
    () => ({ currentUser, login }),
    [currentUser, login],
  )

  return <AuthContext value={value}>{children}</AuthContext>
}
```

Now consumers only re-render when `currentUser` actually changes, not whenever
`AuthProvider` happens to render.

**Split state from dispatch.** With `useReducer`, the dispatch function is
stable for the lifetime of the component, so putting it in its own context means
components that only *write* never re-render when the state changes:

```jsx
const TodosContext = createContext(null)
const TodosDispatchContext = createContext(null)

function TodosProvider({ children }) {
  const [todos, dispatch] = useReducer(todosReducer, [])

  return (
    <TodosContext value={todos}>
      <TodosDispatchContext value={dispatch}>{children}</TodosDispatchContext>
    </TodosContext>
  )
}
```

An "Add todo" button reads only `TodosDispatchContext` and never re-renders as
the list grows. This is the single highest-value Context pattern.

</Level>

<Level value="advanced">

**Split contexts by update frequency, not by domain.** Since there's no
selector, the granularity of your contexts *is* your re-render granularity. If
one value changes per session and another changes per keystroke, they belong in
different contexts even if they feel like one feature:

```jsx
// Changes rarely — safe for the whole app to consume.
const SessionContext = createContext(null)

// Changes constantly — keep its consumers few and shallow.
const DraftContext = createContext(null)
```

This is the technique that keeps Context viable longer than people expect. It's
also the point of diminishing returns: once you're maintaining several contexts
purely to control re-renders, you're hand-rolling what a library gives you for
free, and it's time to switch.

**`use` can read context conditionally.** Unlike `useContext`, it isn't bound by
the rules of hooks, so it may be called inside branches and loops:

```jsx
import { use } from 'react'

function HorizontalRule({ show }) {
  if (show) {
    const theme = use(ThemeContext)
    return <hr className={theme} />
  }
  return null
}
```

Like `useContext`, it finds the closest provider *above* the calling component —
a component cannot read a context it provides itself.

**Scope a value per subtree, not per app.** Nesting providers overrides the value
for that branch, which is genuinely hard to do with a module-level store and is
Context's real structural advantage:

```jsx
<ThemeContext value="dark">
  <Sidebar />
  <ThemeContext value="light">
    <Modal /> {/* reads "light" */}
  </ThemeContext>
</ThemeContext>
```

The same trick handles per-request state on the server: create the value inside
the request-scoped component rather than at module level, and two concurrent
requests can never see each other's data.

**When to graduate.** Concretely, leave Context when you hit any of these:

- Consumers re-render measurably too often and splitting contexts hasn't fixed it
- You want to read or write the value from outside React
- You need the value to survive unmounting the provider
- You're writing your own subscription layer on top of it

Short of those, the built-in is genuinely enough, and it's one fewer dependency.

</Level>

</DifficultyTabs>
