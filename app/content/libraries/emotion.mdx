## Introduction

Emotion is a runtime CSS-in-JS library. You write styles in JavaScript, and it
generates real CSS with hashed, collision-proof class names, injecting them into
the document as components render. Current major version: **v11**
(`@emotion/react` 11.14.0, `@emotion/styled` 11.14.1).

It comes in two flavours, and picking the right one matters:

- **`@emotion/react`** — the React-aware package. Gives you the `css` prop,
  theming, and `Global`. Needs a small build configuration.
- **`@emotion/css`** — framework-agnostic, no build step, no babel plugin. Call
  a function, get a class name string.

Most React projects want the first. The second is useful in non-React code or
where you can't touch the build config.

## Where it stands today

Worth knowing before you adopt it on something new. Emotion is **stable but
slow-moving**: `@emotion/react` 11.14.0 shipped in December 2024, and the
project describes itself as being in a phase of small improvements rather than
new features.

The React 19 situation is more nuanced than most write-ups suggest. You'll find
posts saying installs fail against React 19 and that you need
`--legacy-peer-deps` — that's now out of date. The published peer range is
`react: >=16.8.0`, which React 19 satisfies, so installation works. What's still
outstanding is *official* full React 19 support, which maintainers have said is
coming in v12; v12 has not been released.

The deeper constraint is architectural: runtime CSS-in-JS cannot run in React
Server Components, because there is no client runtime to inject styles. If
you're heading toward an RSC-based framework, this is the thing to weigh, not
the version numbers.

## The css prop needs build setup

Unlike `styled`, the `css` prop isn't plain JavaScript — it requires the JSX
factory to be Emotion's. Either mark individual files with a pragma comment:

```jsx
/** @jsxImportSource @emotion/react */
```

…or configure it once for the whole project, which is what most setups do. See
the Medium tab for the Vite configuration.

Forgetting this is the classic first-time failure: the `css` prop is silently
passed through to the DOM as an unknown attribute and no styles appear.

<Level value="easy">

```bash
npm install @emotion/react @emotion/styled
```

The **`styled` API** creates a component with styles attached. It needs no
special build configuration:

```jsx
import styled from '@emotion/styled'

const Button = styled.button`
  padding: 0.5rem 1rem;
  border-radius: 8px;
  background: #4f46e5;
  color: white;
`

function App() {
  return <Button onClick={save}>Save</Button>
}
```

Styles can read props, which is the whole point of CSS-in-JS:

```jsx
const Button = styled.button`
  background: ${(props) => (props.variant === 'danger' ? '#dc2626' : '#4f46e5')};
  opacity: ${(props) => (props.disabled ? 0.5 : 1)};
`
```

The **`css` prop** styles an element directly, without naming a component —
useful for one-offs:

```jsx
/** @jsxImportSource @emotion/react */
import { css } from '@emotion/react'

function Notice() {
  return (
    <p
      css={css`
        padding: 1rem;
        border-left: 3px solid #4f46e5;
      `}
    >
      Heads up.
    </p>
  )
}
```

Object syntax works everywhere template literals do, and is easier to compose
programmatically:

```jsx
<p css={{ padding: '1rem', color: 'rebeccapurple' }} />
```

</Level>

<Level value="medium">

**Configure the JSX import source once** instead of adding a pragma to every
file. With Vite:

```js
// vite.config.js
import react from '@vitejs/plugin-react'
import { defineConfig } from 'vite'

export default defineConfig({
  plugins: [
    react({
      jsxImportSource: '@emotion/react',
      babel: { plugins: ['@emotion/babel-plugin'] },
    }),
  ],
})
```

For TypeScript to accept the `css` prop on every element, point the compiler at
the same factory:

```json
{
  "compilerOptions": {
    "jsx": "react-jsx",
    "jsxImportSource": "@emotion/react"
  }
}
```

`@emotion/babel-plugin` is optional but worth adding — it produces readable class
names in development and enables source maps back to the original style
definition.

**Composition is just values.** Because a `css` block is an object, styles
compose by array, with later entries winning:

```jsx
const base = css`
  padding: 0.5rem 1rem;
  border-radius: 8px;
`

const danger = css`
  background: #dc2626;
`

<button css={[base, danger]} />
```

This is Emotion's real advantage over `styled`-only libraries: no wrapper
components needed to combine styles.

**Theming** passes a theme object down and makes it available to every style
function:

```jsx
import { ThemeProvider } from '@emotion/react'

const theme = { colors: { primary: '#4f46e5' } }

<ThemeProvider theme={theme}>
  <App />
</ThemeProvider>
```

```jsx
const Title = styled.h1`
  color: ${(props) => props.theme.colors.primary};
`

// Or with the css prop, which accepts a function of the theme:
<h1 css={(theme) => ({ color: theme.colors.primary })} />
```

**Global styles and keyframes** have dedicated APIs:

```jsx
import { Global, css, keyframes } from '@emotion/react'

const fadeIn = keyframes`
  from { opacity: 0; }
  to { opacity: 1; }
`

<Global
  styles={css`
    body { margin: 0; font-family: system-ui; }
  `}
/>

<div css={{ animation: `${fadeIn} 200ms ease-out` }} />
```

</Level>

<Level value="advanced">

**Styling other components.** `styled` wraps any component that accepts a
`className`, which is how you extend a third-party component or one of your own:

```jsx
const Link = styled(RouterLink)`
  color: inherit;
  text-decoration: none;
`
```

If a wrapped component doesn't apply the `className` it receives, nothing
happens — that's the first thing to check when styling a library component does
nothing.

**Stop invalid props reaching the DOM.** Styling props are passed through to the
underlying element by default, and React warns about unknown attributes. Use
`shouldForwardProp` to filter them:

```jsx
import isPropValid from '@emotion/is-prop-valid'

const Button = styled('button', {
  shouldForwardProp: (prop) => isPropValid(prop) && prop !== 'variant',
})`
  background: ${(props) => (props.variant === 'danger' ? 'red' : 'blue')};
`
```

A common convention is prefixing styling-only props with `$` and filtering those.

**Keep dynamic styles narrow.** Every distinct interpolation result produces a
new serialised class, so a style that varies continuously creates unbounded
classes:

```jsx
// Bad — a new class on every pixel of movement.
<div css={{ transform: `translateX(${x}px)` }} />

// Better — one class, a variable that changes.
<div css={{ transform: 'translateX(var(--x))' }} style={{ '--x': `${x}px` }} />
```

Splitting a component's styles into a static block plus a small dynamic block is
the general form of this, and it's the single biggest runtime win available.

**The `ClassNames` escape hatch** gives you a generated class name as a string,
for APIs that want `className` rather than styles:

```jsx
import { ClassNames } from '@emotion/react'

<ClassNames>
  {({ css }) => (
    <ThirdPartyThing classes={{ root: css({ color: 'hotpink' }) }} />
  )}
</ClassNames>
```

**No build step at all?** `@emotion/css` returns class-name strings directly. It
works outside React and needs no pragma, plugin, or tsconfig change — at the
cost of theming and the `css` prop:

```js
import { css, cx } from '@emotion/css'

const box = css`
  padding: 1rem;
`

element.className = cx(box, isActive && css`outline: 2px solid;`)
```

**Server rendering.** Emotion extracts critical styles during SSR, but the
integration differs per framework, and it cannot work inside React Server
Components — those render without a client runtime, so there is nothing to
inject styles. Plan for a build-time solution in RSC-heavy applications.
