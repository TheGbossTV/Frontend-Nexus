## Introduction

React Testing Library renders components into a DOM and gives you queries for
finding things inside them. Current major version: **v16**
(`@testing-library/react` 16.3.x), supporting React 18 and 19.

It is not a test runner. It has no `describe`, no `expect`, no watch mode — you
bring Vitest or Jest for that. What it provides is `render` plus a set of
queries.

The guiding principle is stated in its own docs: *the more your tests resemble
the way your software is used, the more confidence they can give you.* In
practice that means querying the way a person would — "the button labelled Save"
— rather than the way a developer might reach for it, by CSS class or component
instance.

The payoff is that tests survive refactoring. Rename a component, restructure
the markup, or swap a styling approach, and a test asserting on visible
behaviour still passes. A test asserting on internal state breaks for no good
reason.

## Query priority is the core skill

Most of getting good at this library is picking the right query. The
recommended order, best first:

1. **`getByRole`** — with the `name` option. Matches the accessibility tree, so
   it checks what assistive technology exposes. Covers most cases.
2. **`getByLabelText`** — for form fields; also verifies the label is properly
   associated.
3. **`getByPlaceholderText`**, **`getByText`**, **`getByDisplayValue`**.
4. **`getByAltText`**, **`getByTitle`**.
5. **`getByTestId`** — the escape hatch, for things with no accessible handle.

If you can't find an element by role or label, that's often a real
accessibility problem rather than a testing inconvenience — an icon-only button
with no accessible name, say. The awkward test is a signal.

Each query has three variants, and mixing them up causes most confusing
failures:

- **`getBy…`** — throws if not found. Use when it must exist now.
- **`queryBy…`** — returns `null` if not found. **The only one to use for
  asserting absence.**
- **`findBy…`** — returns a promise, retrying until it appears. Use for anything
  async.

## Quick Reference

Three packages in play: `@testing-library/react` for rendering and queries,
`@testing-library/user-event` for interaction, `@testing-library/jest-dom` for
the matchers.

- `render(<Component />)` — mounts into a container and returns the query set plus `rerender` and `unmount`.
- `screen` — the same queries bound to `document.body`; the usual way to reach them.
- `screen.getByRole(role, { name })` — the query to try first; matches the accessibility tree.
- `screen.getByLabelText(text)` — form fields, by their associated label.
- `screen.getByText(text)` — visible text content.
- `screen.getByTestId(id)` — the escape hatch, for elements with no accessible handle.
- `queryBy…` — returns `null` instead of throwing; the variant to use for asserting absence.
- `findBy…` — returns a promise and retries, for anything that appears asynchronously.
- `…AllBy…` — the plural form of any query, returning an array.
- `within(element)` — scopes queries to a subtree, for one row of a table or one card in a list.
- `rerender(<Component />)` — re-renders with new props, keeping the same mount.
- `renderHook(fn)` — tests a hook in isolation, exposing its return value as `result.current`.
- `waitFor(fn)` — retries an assertion until it passes or times out.
- `waitForElementToBeRemoved(fn)` — waits for something to disappear, such as a spinner.
- `act(fn)` — wraps state updates React would otherwise warn about; rarely needed directly.
- `cleanup()` — unmounts between tests; automatic under Vitest and Jest with globals enabled.
- `userEvent.setup()` — call it *before* `render`; returns the interaction API.
- `user.click(element)` — a full click, with the hover and focus events a real one fires.
- `user.type(element, text)` — types character by character, firing each key event.
- `user.keyboard(text)` — key presses without a target, for shortcuts and `{Enter}`.
- `user.clear(element)` — empties an input.
- `user.selectOptions(select, value)` — picks from a `<select>`.
- `user.upload(input, file)` — attaches a file to a file input.
- `user.tab()` — moves focus, for testing keyboard navigation order.
- `fireEvent.change(element, init)` — dispatches one raw DOM event; the lower-level fallback.
- `expect(el).toBeInTheDocument()` — asserts presence.
- `expect(el).toBeVisible()` — asserts it's actually visible, not just present.
- `expect(el).toBeDisabled()` / `.toBeChecked()` — asserts control state.
- `expect(el).toHaveValue(value)` — asserts a form control's value.
- `expect(el).toHaveTextContent(text)` — asserts text, including from descendants.
- `expect(el).toHaveAccessibleName(name)` — asserts what a screen reader would announce.

<Level value="easy">

Install the library, the DOM matchers, and — since v16 — `@testing-library/dom`
explicitly, because it's a peer dependency rather than bundled:

```bash
npm install -D @testing-library/react @testing-library/dom @testing-library/jest-dom @testing-library/user-event
```

With Vitest, one setup file wires up the matchers and cleanup:

```ts
// vitest.setup.ts
import '@testing-library/jest-dom/vitest'
```

```ts
// vite.config.ts
export default defineConfig({
  test: {
    environment: 'jsdom',
    globals: true,
    setupFiles: ['./vitest.setup.ts'],
  },
})
```

The `/vitest` entry point registers every jest-dom matcher on Vitest's `expect`.
With `globals: true`, cleanup between tests is automatic.

A first test:

```jsx
import { render, screen } from '@testing-library/react'
import { expect, it } from 'vitest'
import { Greeting } from './Greeting'

it('greets the user by name', () => {
  render(<Greeting name="Ada" />)

  expect(screen.getByRole('heading', { name: 'Hello, Ada' })).toBeVisible()
})
```

`screen` queries the whole document, which saves destructuring the return value
of `render`.

jest-dom is what makes the assertions readable, and its failure messages far more
useful than a bare truthiness check:

```js
expect(element).toBeInTheDocument()
expect(element).toBeVisible()
expect(button).toBeDisabled()
expect(input).toHaveValue('hello')
expect(checkbox).toBeChecked()
expect(element).toHaveTextContent('Saved')
```

<Level value="medium">

**Use `user-event`, not `fireEvent`.** `fireEvent` dispatches a single DOM event;
`user-event` simulates the whole interaction — focus, key events, input events —
and refuses to act on hidden or disabled elements, exactly as a browser would.

In v14 you call `setup()` first and `await` every interaction:

```jsx
import userEvent from '@testing-library/user-event'

it('submits the form', async () => {
  const user = userEvent.setup()
  const onSubmit = vi.fn()

  render(<LoginForm onSubmit={onSubmit} />)

  await user.type(screen.getByLabelText('Email'), 'ada@example.com')
  await user.click(screen.getByRole('button', { name: 'Log in' }))

  expect(onSubmit).toHaveBeenCalledWith({ email: 'ada@example.com' })
})
```

Forgetting `await` is the most common source of flaky Testing Library tests.

**Async results use `findBy`**, which retries until the element appears or times
out:

```jsx
it('shows todos once loaded', async () => {
  render(<Todos />)

  expect(screen.getByText('Loading…')).toBeInTheDocument()

  // Waits for the element rather than guessing at a delay.
  expect(await screen.findByRole('list')).toBeInTheDocument()
})
```

**Asserting something is absent** requires `queryBy`, because `getBy` throws
before your assertion runs:

```jsx
expect(screen.queryByRole('alert')).not.toBeInTheDocument()
```

For something that disappears, wait for it explicitly:

```jsx
await waitForElementToBeRemoved(() => screen.queryByText('Loading…'))
```

**`within` scopes a query** to part of the tree, which matters when the same
text appears more than once:

```jsx
const row = screen.getByRole('row', { name: /Ada/ })
await user.click(within(row).getByRole('button', { name: 'Delete' }))
```

**When a query fails**, print the DOM rather than guessing:

```jsx
screen.debug()                       // whole document
screen.debug(screen.getByRole('form')) // one element
screen.logTestingPlaygroundURL()     // opens a query builder for the markup
```

</Level>

<Level value="advanced">

**Wrap providers in a custom render** so no test has to remember them. Re-export
everything from the library so tests only import one module:

```jsx
// test-utils.jsx
import { render } from '@testing-library/react'
import { QueryClient, QueryClientProvider } from '@tanstack/react-query'

function AllProviders({ children }) {
  // A fresh client per test — otherwise cache leaks between tests.
  const queryClient = new QueryClient({
    defaultOptions: { queries: { retry: false } },
  })

  return (
    <QueryClientProvider client={queryClient}>
      <ThemeProvider>{children}</ThemeProvider>
    </QueryClientProvider>
  )
}

export * from '@testing-library/react'
export function renderWithProviders(ui, options) {
  return render(ui, { wrapper: AllProviders, ...options })
}
```

Disabling retries matters: a query library retrying a deliberately failing
request will hang your test until it times out.

**Test hooks directly** with `renderHook` when the logic doesn't belong to one
component:

```jsx
import { act, renderHook } from '@testing-library/react'

it('increments', () => {
  const { result } = renderHook(() => useCounter())

  act(() => result.current.increment())

  expect(result.current.count).toBe(1)
})
```

`result.current` is re-read after each render, so never destructure it up front —
you'd be holding a stale value.

**About `act` warnings.** They mean state updated outside React's knowledge —
almost always an async update finishing after the test moved on. The fix is
usually to await the thing you were waiting for rather than to wrap more code in
`act`:

```jsx
// Warns: the fetch resolves after the test body ends.
render(<Profile />)
expect(screen.getByText('Ada')).toBeInTheDocument()

// Correct: wait for the update.
render(<Profile />)
expect(await screen.findByText('Ada')).toBeInTheDocument()
```

`user-event` and the `findBy` queries wrap `act` internally, which is another
reason to prefer them.

**Accessible names come from more than text.** `getByRole('button', { name })`
matches the computed accessible name, so these all work:

```jsx
<button>Save</button>                             // name: "Save"
<button aria-label="Close dialog">×</button>      // name: "Close dialog"
<button><VisuallyHidden>Delete</VisuallyHidden><TrashIcon /></button>
```

If a role query can't find your element, `screen.getByRole('button')` with no
name will list every button and its computed name in the failure output.

**What not to test.** Skip assertions on internal state, prop values, or which
child component rendered — those are implementation, and testing them makes
refactoring expensive without catching real bugs. Assert on what the user would
see and what your code calls outward, such as a submit handler receiving the
right payload.

</Level>
